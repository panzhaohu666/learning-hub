### 手机摸鱼 · 上午 30 分钟
阅读主题：什么是大语言模型（LLM）

> **🧠 在你开始读之前，记住这个类比：LLM 就像一个读过整个图书馆的人。你问它问题，它不是"思考"，而是在已读的所有书里快速搜索相关的内容，然后续写最合理的下一句。它没有意识——但它模拟出的回答，足以让 90% 的人觉得它是"智能"的。**

核心知识点（直接看这里，不需要查资料）

1. LLM 是什么？

大语言模型（Large Language Model）本质上是一个"下一个词预测器"。
你给它一段文字，它预测接下来最可能出现的词是什么。

比如你输入 "今天天气真"，模型会计算：
好 → 概率 60%
热 → 概率 25%
冷 → 概率 10%
差 → 概率 5%

然后选择概率最高的词输出。如此反复，就形成了连贯的文本。

**🧩 类比**：想象你在和一个非常博学但只会"接话"的人聊天。你说"床前明月"，他会条件反射般接"光"——不是因为他看到了月光，而是因为他读过足够多的唐诗，知道"床前明月"后面 99% 的情况下跟着"光"。LLM 也是这个原理——它读的文本量相当于一个人不吃不喝读 5 万年的书。

关键洞察：当模型足够大（千亿参数），"预测下一个词"这个简单任务
会迫使模型学会理解语法、推理、甚至逻辑——因为只有理解了上下文，
才能准确预测下一个词。

2. 三个核心概念

Token（词元）
- 模型不认识"字"，只认识"Token"
- 一个 Token ≈ 0.75 个英文单词 ≈ 1-2 个中文字
- 例："我喜欢编程" → ["我", "喜欢", "编程"] 大约 3 个 token
- 为什么重要？模型的上下文窗口是按 Token 算的，API 收费也是

**🧩 类比**：Token 就像"乐高积木"。模型不直接处理"句子"这个整体——它把句子拆成一块块积木（Token），然后预测下一块积木是什么。中文的积木比英文大（每个字信息量大），所以同样意思的中文句子 Token 数通常比英文少。

上下文窗口（Context Window）
- 模型一次能"看到"的最大 Token 数
- GPT-4 Turbo：128K tokens（约 10 万字，相当于一本小说）
- Qwen2-0.5B：32K tokens
- 超过窗口的内容会被截断或遗忘

**🧩 类比**：上下文窗口就像你和一个人聊天时，TA 能记住的"最近说了什么"。如果你们聊了 3 小时，TA 可能忘记了第 1 小时的内容——这和 LLM 的原理一样。所以当你需要模型"记住"很长的信息时，就需要技巧（阶段四的 RAG 就是为此设计的）。

Temperature（温度）
- 控制输出的"随机性"，范围 0~2
- Temperature = 0：每次都选概率最高的词（确定性，适合翻译/代码）
- Temperature = 1：按原始概率分布采样（创造性，适合写文章）
- Temperature > 1：增加低概率词的机会（更"疯狂"的文本）

**🧩 类比**：Temperature 就像厨师的"创意自由度"。T=0 时，厨师严格按照菜谱——宫保鸡丁就是宫保鸡丁，每次味道一模一样。T=1 时，厨师会根据自己的感觉微调——还是宫保鸡丁，但今天的可能偏甜一点。T=2 时，厨师开始放飞——宫保鸡丁里可能出现了巧克力。对于代码生成，你要 T=0（一致性）；对于创意写作，你要 T=0.7-1.0（多样性）。

3. 训练 vs 推理 vs 微调

训练（Training）：从头训练模型，需要海量数据和算力（数百万美元）
微调（Fine-tuning）：在预训练模型上继续训练少量数据（几百到几千美元）
推理（Inference）：用训练好的模型生成文本（最便宜，按 token 计费）

**🧩 类比**：
- 训练 = 从零培养一个医生（8 年医学院，数百万投入）
- 微调 = 让一个全科医生进修心脏病学（几个月的专科培训）
- 推理 = 让医生看诊（每次门诊收费）

你的学习路线：先用现成模型做推理 → 学会微调 → 理解训练原理

        messages.append({"role": "user", "content": user_input})

        response = client.chat.completions.create(
            model="qwen2:0.5b",
            messages=messages,
            temperature=0.7
        )

        reply = response.choices[0].message.content
        print(f"Bot: {reply}")

        messages.append({"role": "assistant", "content": reply})

if __name__ == "__main__":
    chat()

### 手机摸鱼 · 上午 30 分钟
阅读主题：Prompt 工程基础 —— Zero-shot 和 Few-shot

> **🍳 Prompt Chef 类比**：把 LLM 想象成一个超级厨房。你给它的 Prompt 就是"菜谱"。菜谱写得好（步骤清晰、食材明确），出来的菜就好吃。菜谱写得模糊（"做点好吃的"），厨房就会自由发挥——有时惊喜，有时灾难。好的 Prompt Engineer 就是一个好厨师：知道什么菜谱适合什么场景，知道什么时候给示例（Few-shot），什么时候信任厨房的处理能力（Zero-shot）。

核心知识点

1. 什么是 Prompt Engineering？

Prompt（提示词）就是你给模型的输入指令。Prompt Engineering 是
设计有效指令来引导模型产生期望输出的技术。

核心原则：模型不会"读懂你的心"，你给的指令越清晰具体，输出越好。

坏 Prompt：  "写一个总结"
好 Prompt：  "用 3 句话总结以下文章的核心观点，每句话不超过 20 个字"

2. Zero-shot Prompting（零样本提示）

直接给任务，不给示例。适用于模型已经"知道"的任务。

**🍳 类比**：Zero-shot 就是对厨师说"做一盘宫保鸡丁"——不需要教，因为这是经典菜，每个厨师都会。

示例：
请判断以下句子的情感是正面还是负面：
"这家餐厅的服务太棒了，食物也很好吃！"
情感：

模型输出：正面 ✓

Zero-shot 适用于：
- 翻译、摘要、分类等"标准"任务
- 模型训练数据中充分覆盖的任务

3. Few-shot Prompting（少样本提示）

给模型几个示例，再让它做新任务。适用于格式要求严格或
任务比较特殊的场景。

**🍳 类比**：Few-shot 就是对厨师说"我要的宫保鸡丁是这样的——上次 XX 餐厅的那种，花生多放、花椒少放、鸡肉切丁不要切条"。给几个具体的参考案例，厨师就能精确复制你的口味。

示例：
将以下句子从中文翻译成英文，保持相同的语气。

示例 1：
中文：今天天气真好
英文：The weather is really nice today

示例 2：
中文：我昨天去了电影院
英文：I went to the cinema yesterday

现在翻译：
中文：这本书非常有趣

模型输出：This book is very interesting ✓

Few-shot 的要点：
- 2-5 个示例通常足够
- 示例的格式要和期望输出完全一致
- 示例要覆盖任务的不同情况

建文件 prompt_compare.py：
用 Zero-shot 和 Few-shot 分别做同一个任务（情感分类），
看谁的准确率更高。

```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

# 测试数据
test_cases = [
    ("等待了2个小时菜才上来，太失望了", "负面"),
    ("性价比很高，下次还会来", "正面"),
    ("环境还行，服务一般般吧", "中性"),
    ("这家店简直是宝藏！强烈推荐！", "正面"),
    ("分量太少了，完全吃不饱", "负面"),
]

# Zero-shot Prompt
zero_shot_prompt = """
判断以下句子的情感是正面、负面还是中性。只回答一个词。
句子：{text}
情感：
"""

# Few-shot Prompt
few_shot_prompt = """
判断以下句子的情感是正面、负面还是中性。只回答一个词。

示例：
句子：味道很不错，下次还来  情感：正面
句子：服务态度极差，气死了  情感：负面
句子：还可以吧，中规中矩  情感：中性

句子：{text}
情感：
"""

def test_prompt(name, prompt_template):
    correct = 0
    for text, expected in test_cases:
        prompt = prompt_template.format(text=text)
        response = client.chat.completions.create(
            model="qwen2:0.5b",
            messages=[{"role": "user", "content": prompt}],
            temperature=0  # 温度=0 保证确定性
        )
        result = response.choices[0].message.content.strip()
        is_correct = expected in result
        if is_correct:
            correct += 1
        print(f"  [{('✓' if is_correct else '✗')}] {text} → {result} (期望: {expected})")
    print(f"  {name} 准确率: {correct}/{len(test_cases)}")

print("=== Zero-shot 测试 ===\n")
test_prompt("Zero-shot", zero_shot_prompt)

print("\n=== Few-shot 测试 ===\n")
test_prompt("Few-shot", few_shot_prompt)
```

运行后观察：Few-shot 通常比 Zero-shot 准确率更高。

### 手机摸鱼 · 上午 30 分钟
阅读主题：Chain-of-Thought（思维链）Prompting

> **🧩 类比**：如果 Zero-shot 是直接问"答案是什么"，那 CoT 就是让模型"把解题步骤写下来"。就像你在考场上——直接蒙一个答案和先写推导过程再给答案，正确率天差地别。模型的"思考"不是在脑子里的——它写在文本里，而每写一步，前面写的都变成了后续推理的"上下文"。这就是 CoT 能大幅提升推理能力的原因。

核心知识点

1. 问题：大模型能做数学题吗？

Prompt：356 × 27 = ?
模型直接回答：9612

这个答案可能是对的（巧合），也可能是错的。问题在于：
模型没有"思考过程"，直接在赌一个答案。

2. Chain-of-Thought（思维链）

解决方法是：让模型先写出推理过程，再给答案。

Prompt（加一句话）：
356 × 27 = ? 请一步一步推理。

模型输出：
356 × 20 = 7120
356 × 7 = 2492
7120 + 2492 = 9612
所以答案是 9612。

为什么有效？因为：
- 模型每生成一个 token 时，前面生成的 token 都在上下文窗口中
- 写出中间步骤相当于让模型"看到"了更多相关信息
- 这大大提高了复杂推理的准确率

3. CoT 的标准写法

最简单的 CoT：在 Prompt 末尾加一句"让我们一步一步思考"。
英文：Let's think step by step.
这句魔法话在很多任务上都能显著提升效果。

Few-shot CoT：在示例中展示推理过程。

示例：
问题：小明有 5 个苹果，小红给了他 3 个，然后他吃了 2 个。
小明现在有几个苹果？

推理：
- 小明开始有 5 个苹果
- 小红给了 3 个 → 5 + 3 = 8
- 吃掉了 2 个 → 8 - 2 = 6
- 所以小明现在有 6 个苹果
答案：6

问题：一个长方形长 8 米，宽 5 米，它的面积是多少？

模型会模仿上面的格式，写出推理过程。

4. CoT 的局限
- 对简单任务没有帮助，甚至可能"想太多"而搞错
- CoT 本身不验证推理是否正确——模型可能在推理中犯错
- 比较适合：数学、逻辑、常识推理

核心知识点

1. 模型分为两大类

闭源模型（商业 API）：
- 部署在厂商服务器上，按 token 付费
- 优点：效果最好，开箱即用
- 缺点：贵、数据要传给厂商、不能定制

开源模型（自己部署）：
- 下载到自己的服务器上运行
- 优点：可控、数据不外传、可以微调
- 缺点：需要 GPU、效果可能不如闭源

**🧩 类比**：闭源模型就像米其林餐厅——最好吃但最贵，还不能进厨房看怎么做。开源模型就像你家厨房——想做什么做什么，数据不外泄，但需要自己买菜、备料、掌握火候。

2. 主要模型一览

GPT-4 / GPT-4o (OpenAI)
- 目前最强的通用模型之一
- 支持多模态（文字+图片+语音）
- 价格：输入 $2.5/1M tokens，输出 $10/1M tokens

Claude 3.5 (Anthropic)
- 长文本处理能力特别强（200K 上下文）
- 安全性好，幻觉率低
- 编程能力突出

DeepSeek-V3 / DeepSeek-R1 (深度求索)
- 国产最强模型，开源
- R1 主打推理能力（可以显式输出 CoT）
- API 价格极低：输入 ¥1/1M tokens
- 手机/电脑都支持，响应快

Qwen 系列（阿里通义千问）
- 国产开源模型的标杆
- 从 0.5B 到 72B 多种规格
- 中文能力优秀
- Qwen2-0.5B 可以在普通电脑上运行（你本地跑的那个）

ChatGLM (智谱)
- 清华出品，中文对话效果好
- GLM-4 已在多个榜单赶上 GPT-4

3. 如何在它们之间选择？

学习阶段：DeepSeek API（便宜）+ Qwen 本地（免费）
生产环境：GPT-4（质量最好）或 DeepSeek（性价比）
微调基座：Qwen / LLaMA（开源，生态好）

4. 开源 vs 闭源的选择策略
闭源用在哪：快速验证想法、对质量要求极高的场景
开源用在哪：数据敏感的、需要微调的、大量调用的（省钱）

```python
import json
import os
from openai import OpenAI

MEMORY_FILE = "chat_memory.json"
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

def load_memory():
    """从文件加载对话历史"""
    if os.path.exists(MEMORY_FILE):
        with open(MEMORY_FILE, "r", encoding="utf-8") as f:
            return json.load(f)
    return [{"role": "system", "content": "你是一个友好的助手，用中文回答"}]

def save_memory(messages):
    """保存对话历史到文件"""
    with open(MEMORY_FILE, "w", encoding="utf-8") as f:
        json.dump(messages, f, ensure_ascii=False, indent=2)

def chat():
    messages = load_memory()
    print(f"ChatBot 已启动！已加载 {len(messages)-1} 条历史记录。")
    print("输入 'quit' 退出，输入 'clear' 清除记忆。\n")

    while True:
        user_input = input("你: ")
        if user_input.lower() == 'quit':
            save_memory(messages)
            print(f"已保存 {len(messages)-1} 条对话记录。再见！")
            break
        if user_input.lower() == 'clear':
            messages = [messages[0]]  # 只保留 system prompt
            save_memory(messages)
            print("记忆已清除！")
            continue

        messages.append({"role": "user", "content": user_input})
        response = client.chat.completions.create(
            model="qwen2:0.5b",
            messages=messages,
            temperature=0.7
        )
        reply = response.choices[0].message.content
        print(f"Bot: {reply}")
        messages.append({"role": "assistant", "content": reply})

if __name__ == "__main__":
    chat()
```

核心知识点

1. 为什么需要控制输出格式？

目前为止，模型输出都是自由文本。但实际应用中，我们经常
需要模型输出结构化数据（JSON），这样代码才能自动处理。

例如：做一个客服机器人，你需要模型返回：
{
"intent": "退货",
"sentiment": "负面",
"summary": "用户收到的商品破损，要求退货退款"
}

而不是一段自由文本。因为后续的系统需要根据 intent 字段
来决定走哪条处理流程。

2. 如何让模型输出 JSON？

方法 1：在 Prompt 中明确要求
"请用 JSON 格式回答，包含 intent、sentiment、summary 三个字段"

方法 2：给 JSON 示例（Few-shot）
在示例中展示你期望的 JSON 结构

方法 3：使用 LLM 的 JSON Mode（如果有的话）
部分模型支持设置 response_format={"type": "json_object"}

3. 结构化 Prompt 的通用模板

```markdown
## 角色
你是一个客服意图分析助手

## 任务
分析用户的消息，判断意图、情感和关键信息

## 输出格式
严格的 JSON，包含以下字段：
- intent: 用户意图（咨询/投诉/退货/购买）
- sentiment: 情感倾向（正面/负面/中性）
- summary: 一句话总结

## 示例
输入："这个东西太差了，我要退款"
输出：{"intent": "退货", "sentiment": "负面", "summary": "用户对商品不满意要求退款"}

## 用户消息
{user_message}
```

import json
from openai import OpenAI
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

SYSTEM_PROMPT = """你是一个客服意图分析助手。
分析用户消息，返回 JSON 格式结果。

字段说明：
- intent: 用户意图，只能是以下之一：咨询、投诉、退货、购买、闲聊
- sentiment: 情感倾向，只能是：正面、负面、中性
- summary: 一句话总结用户的问题
- urgency: 紧急程度，1-5 分（1=不急，5=非常紧急）

示例：
输入："你们这个产品质量太差了，我要退款！"
输出：{"intent":"退货","sentiment":"负面","summary":"用户对产品质量不满要求退款","urgency":4}

注意：只输出 JSON，不要输出其他内容。"""

def classify_intent(user_message):
    response = client.chat.completions.create(
        model="qwen2:0.5b",
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": f"用户消息：{user_message}"}
        ],
        temperature=0
    )
    raw = response.choices[0].message.content.strip()
    # 尝试提取 JSON（有些模型会在 JSON 外面包 markdown 代码块）
    if raw.startswith("```"):
        raw = raw.split("\n", 1)[1]
        if raw.endswith("```"):
            raw = raw[:-3]
    try:
        return json.loads(raw)
    except json.JSONDecodeError:
        return {"error": "JSON 解析失败", "raw": raw}

# 测试
test_messages = [

    "收到的手机屏幕碎了，我要退货",
    "今天天气不错",
]

for msg in test_messages:
    result = classify_intent(msg)
    print(f"输入: {msg}")
    print(f"结果: {json.dumps(result, ensure_ascii=False)}")

### 手机摸鱼 · 上午 30 分钟
阅读主题：Function Calling（工具调用）—— 让模型"做事"

> **📞 个人助理类比**：Function Calling 就像你给助理配了一部手机。在此之前，助理只能根据 TA 已有的知识回答你（"我觉得今天天气应该不错"）。配了手机之后，你可以说"帮我查一下北京的天气"，助理拿起手机打给气象台，得到准确信息后再告诉你（"北京今天晴，25°C"）。**模型就是你的助理，Function Calling 就是那部手机——模型不直接"做"事情，而是"决定"要打什么电话、传什么参数，你的代码负责真正"打电话"。**

核心知识点

1. 问题：模型被困在"对话"里

目前为止，模型只能输出文本。它不能：
- 查今天的天气
- 计算精确的数学题
- 搜索互联网
- 操作数据库

但很多实际应用需要这些能力。怎么办？

2. Function Calling 的思路

模型不直接执行函数。而是：
1. 你告诉模型有哪些"工具"可用（函数名 + 描述 + 参数）
2. 模型根据用户输入，决定要不要调用工具
3. 如果需要，模型输出一个"工具调用请求"（JSON）
4. 你的代码解析这个请求，实际执行函数
5. 把函数返回结果再发给模型
6. 模型基于结果生成最终回复

模型只负责"决策"（要不要调、调哪个、传什么参数），
你的代码负责"执行"。

3. 一个简单的例子

你定义了一个函数：

```python
def get_weather(city: str) -> str:
    # 实际应用中这里调天气 API
    return f"{city}今天晴，25°C"
```

告诉模型：
"你有一个工具叫 get_weather，输入城市名，返回天气"

用户问："北京今天天气怎么样？"
模型输出：调用 get_weather(city="北京")
你的代码执行后得到结果"北京今天晴，25°C"
模型最终回复："北京今天天气晴，气温 25°C，适合出门哦！"

4. 为什么能这样？
LLM 的 API 提供了专门的 tool_use / function_calling 功能。
你传 tools 参数给 API，模型会智能判断何时调用。

注：Ollama 对 function calling 的支持有限，今晚用 DeepSeek API。

```python
import json
import math
from openai import OpenAI

client = OpenAI(
    api_key="你的DeepSeek API Key",
    base_url="https://api.deepseek.com"
)

# ========== 定义工具函数 ==========

def get_weather(city: str) -> str:
    """获取城市天气（模拟）"""
    weather_data = {
        "北京": "晴，25°C，湿度40%",
        "上海": "阴，28°C，湿度70%",
        "深圳": "雷阵雨，30°C，湿度85%",
        "杭州": "多云，22°C，湿度55%",
    }
    return weather_data.get(city, f"暂无{city}的天气数据")

def calculate(expression: str) -> str:
    """计算数学表达式"""
    try:
        # 安全检查：只允许数字和基本运算符
        allowed = set("0123456789+-*/().% ")
        if not all(c in allowed for c in expression):
            return "错误：表达式包含不允许的字符"
        result = eval(expression)
        return str(result)
    except Exception as e:
        return f"计算错误: {e}"

def get_current_time() -> str:
    """获取当前时间"""
    from datetime import datetime
    return datetime.now().strftime("%Y年%m月%d日 %H:%M:%S")

# ========== 工具描述（告诉模型有哪些工具可用）==========

TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "获取指定城市的天气信息",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名称，如北京、上海"}
                },
                "required": ["city"]
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "calculate",
            "description": "计算数学表达式，支持加减乘除和括号",
            "parameters": {
                "type": "object",
                "properties": {
                    "expression": {"type": "string", "description": "数学表达式，如 35*12+8"}
                },
                "required": ["expression"]
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "get_current_time",
            "description": "获取当前的日期和时间",
            "parameters": {"type": "object", "properties": {}}
        }
    }
]

# ========== 工具执行映射 ==========

TOOL_MAP = {
    "get_weather": get_weather,
    "calculate": calculate,
    "get_current_time": get_current_time,
}

# ========== 对话循环 ==========

def chat():
    messages = [
        {"role": "system", "content": "你是一个有用的助手，可以使用工具来回答问题。请用中文回复。"}
    ]
    print("智能助手已启动（支持工具调用）！输入 'quit' 退出。\n")

    while True:
        user_input = input("你: ")
        if user_input.lower() == 'quit':
            break

        messages.append({"role": "user", "content": user_input})

        # 第一轮：发给模型，看它要不要调用工具
        response = client.chat.completions.create(
            model="deepseek-chat",
            messages=messages,
            tools=TOOLS,
            temperature=0
        )

        msg = response.choices[0].message

        # 如果模型要调用工具
        if msg.tool_calls:
            # 把模型的工具调用请求加入对话
            messages.append(msg)

            # 逐个执行工具
            for tool_call in msg.tool_calls:
                func_name = tool_call.function.name
                func_args = json.loads(tool_call.function.arguments)

                print(f"  [调用工具: {func_name}({func_args})]")

                func = TOOL_MAP[func_name]
                result = func(**func_args)

                # 把工具执行结果加入对话
                messages.append({
                    "role": "tool",
                    "tool_call_id": tool_call.id,
                    "content": result
                })

            # 第二轮：把工具结果发给模型，让它生成最终回复
            response2 = client.chat.completions.create(
                model="deepseek-chat",
                messages=messages,
                temperature=0
            )
            reply = response2.choices[0].message.content
            messages.append({"role": "assistant", "content": reply})
            print(f"Bot: {reply}")

        else:
            # 模型直接回复
            reply = msg.content
            messages.append({"role": "assistant", "content": reply})
            print(f"Bot: {reply}")

if __name__ == "__main__":
    chat()
```

### 手机摸鱼 · 上午 30 分钟
阅读主题：ReAct 模式 —— 思考 + 行动的循环

> **🧩 类比**：ReAct 就像一个侦探破案。侦探不会在证据不足时直接宣布凶手是谁。TA 会思考（"我需要查什么？"）、行动（去现场收集证据）、观察（"这个指纹是谁的？"）、再思考（"根据新线索，我还需要查什么？"）——直到证据链完整，才给出结论。ReAct Agent 就是这个侦探，只是"收集证据"换成了"调用工具"。

核心知识点

1. 问题：纯 CoT 和纯 Function Calling 各有限制

CoT：只能"想"，不能"做"。推理卡住时无法查资料。
Function Calling：能"做"，但不会主动规划下一步。

理想状态：模型像一个人类一样——
1. 思考需要什么信息
2. 调用工具获取
3. 分析结果
4. 决定下一步
5. 重复直到完成任务

这就是 ReAct（Reasoning + Acting）。

2. ReAct 循环

```
  用户提问
    ↓
  Thought: 我需要先做什么？
    ↓
  Action: 调用工具 X
    ↓
  Observation: 工具返回来什么结果？
    ↓
  Thought: 基于这个结果，我还需要什么？
    ↓
  Action: 调用工具 Y
    ↓
  Observation: 更多结果
    ↓
  ...循环...
    ↓
  Thought: 信息够了，可以回答了
    ↓
  Final Answer: 综合所有信息给出答案
```

3. ReAct vs CoT vs Function Calling

CoT：适合纯推理（数学、逻辑），但不能查外部信息
Function Calling：适合单步工具调用，但不主动规划多步
ReAct：多步推理 + 多轮工具调用，能做复杂任务

例子：用户问"北京和上海今天哪个城市更适合户外活动？"
- CoT：猜（可能不准）
- Function Calling：分别查北京天气、上海天气 → 对比
- ReAct：查天气 → 发现还需要看空气质量 → 再查空气质量 → 综合判断

        {"role": "user", "content": user_query}
    ]

    print(f"用户问: {user_query}\n")
    print("=" * 50)

    for step in range(max_steps):
        print(f"\n--- 第 {step+1} 步 ---")

        response = client.chat.completions.create(
            model="deepseek-chat",
            messages=messages,
            tools=TOOLS,
            temperature=0
        )

        msg = response.choices[0].message

        # 检查是否到了最终答案
        if msg.content and "Final Answer" in msg.content:
            print(f"最终答案: {msg.content.split('Final Answer:')[-1].strip()}")
            return msg.content

        # 需要调用工具
        if msg.tool_calls:
            messages.append(msg)
            for tool_call in msg.tool_calls:
                func_name = tool_call.function.name
                func_args = json.loads(tool_call.function.arguments)

                print(f"  Action: {func_name}({func_args})")
                result = TOOL_MAP[func_name](**func_args)
                print(f"  Observation: {result}")

                messages.append({
                    "role": "tool",
                    "tool_call_id": tool_call.id,
                    "content": result
                })
        else:
            # 没有工具调用也没有 Final Answer → 模型在思考，继续
            if msg.content:
                print(f"  Thought: {msg.content[:200]}")
            messages.append({"role": "assistant", "content": msg.content or ""})

    print("\n已达到最大步数限制")

# ========== 测试 ==========
if __name__ == "__main__":
    # 测试一个需要多步推理的问题
    query = "我想去北京玩，帮我查一下故宫的信息和北京今天的天气，然后计算如果门票60元、交通30元、餐饮50元，总花费是多少？"
    react_agent(query)
