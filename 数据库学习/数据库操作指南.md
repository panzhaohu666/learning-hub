## MySQL 8.x

> **来源**: [MySQL 8.0/8.4 官方参考手册](https://dev.mysql.com/doc/refman/8.0/en/)

### 安装

```bash
# Docker（最简单）
docker run --name mysql -d -p 3306:3306 -e MYSQL_ROOT_PASSWORD=pw mysql:8.4

# Linux (RHEL/CentOS)
dnf install mysql-community-server
systemctl enable --now mysqld
grep 'temporary password' /var/log/mysqld.log
mysql_secure_installation
```

> ⚠️ **MySQL 8.0 认证插件变更**：默认使用 `caching_sha2_password`，部分老客户端（如 PHP 7.3-、旧版 Navicat）可能无法连接。如需兼容，在 `my.cnf` 中添加 `default_authentication_plugin=mysql_native_password`。

> 💡 **关键配置调优** (`my.cnf`)：
> ```ini
> innodb_buffer_pool_size = 4G          # 设为物理内存的 50-70%
> innodb_log_file_size = 1G             # 重做日志大小
> innodb_flush_log_at_trx_commit = 2    # 性能优先时可降为 2（允许丢 1s 数据）
> ```

### CRUD

```sql
-- 建表
CREATE TABLE users (
  id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  email VARCHAR(255) NOT NULL UNIQUE,
  name  VARCHAR(100),
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;

-- 插入
INSERT INTO users (email, name) VALUES ('a@x.com', 'Alice');
INSERT INTO users (email, name) VALUES ('b@x.com','Bob'), ('c@x.com','Cara');

-- 查询
SELECT id, email FROM users WHERE name = 'Alice' ORDER BY id DESC LIMIT 10;

-- 更新
UPDATE users SET name = 'Alicia' WHERE id = 1;

-- 删除（生产环境推荐分块删除）
DELETE FROM audit_log WHERE created_at < NOW() - INTERVAL 90 DAY LIMIT 1000;
```

### 索引

```sql
CREATE INDEX idx_users_email ON users(email);              -- B-tree
CREATE UNIQUE INDEX uk_users_email ON users(email);        -- 唯一索引
CREATE INDEX idx_name ON t(last_name, first_name);         -- 复合索引（左前缀原则）
CREATE FULLTEXT INDEX ft_idx ON articles(title, body);     -- 全文索引
CREATE INDEX idx_hidden ON t(col) INVISIBLE;               -- 隐藏索引（8.0+，测试用）
```

**隐藏索引 (MySQL 8.0+)**：设置 INVISIBLE 后优化器不再使用该索引，适合用来安全测试删除索引的影响。通过 `ALTER TABLE t ALTER INDEX idx_hidden VISIBLE;` 恢复。

```sql
-- 查看索引使用情况（Performance Schema）
SELECT * FROM sys.schema_unused_indexes;
SELECT * FROM sys.schema_redundant_indexes;
```

**复合索引规则**：`(last_name, first_name)` 能加速 `WHERE last_name='Jones'` 和 `WHERE last_name='Jones' AND first_name='John'`，但**不能**加速只查 `first_name` 的查询。

### 查询优化

```sql
-- 查看执行计划
EXPLAIN SELECT * FROM orders WHERE user_id = 1;
EXPLAIN FORMAT=JSON SELECT ...;
```

**EXPLAIN 关键列**：
- `type`: `ALL`(全表扫) → `index` → `range` → `ref` → `eq_ref` → `const`(最优)
- `Extra`: `Using filesort` / `Using temporary` = 红色警报
- `rows`: 预估扫描行数

**慢查询日志**:
```ini
# my.cnf
slow_query_log = 1
long_query_time = 2              # 记录超过2秒的查询
log_queries_not_using_indexes = 1
```

```bash
# 慢查询分析
mysqldumpslow /var/log/mysql/mysql-slow.log       # 需安装 mysql-client 包
pt-query-digest /var/log/mysql/mysql-slow.log      # Percona Toolkit（更强大）
```

### 备份与恢复

```bash
# 逻辑备份（InnoDB一致快照，带binlog坐标）
mysqldump --single-transaction --flush-logs --source-data=2 \
  --all-databases > backup.sql

# 恢复
mysql -u root -p < backup.sql

# 时间点恢复 (PITR)
mysqlbinlog --start-position=155 --stop-position=232 bin.123456 | mysql
```

### 用户管理

```sql
CREATE USER 'appuser'@'10.0.0.%' IDENTIFIED BY 'StrongPass!';
GRANT SELECT, INSERT, UPDATE, DELETE ON appdb.* TO 'appuser'@'10.0.0.%';
SHOW GRANTS FOR 'appuser'@'10.0.0.%';
```

**角色 (8.0+)**:
```sql
CREATE ROLE 'app_read', 'app_write';
GRANT SELECT ON appdb.* TO 'app_read';
GRANT INSERT, UPDATE, DELETE ON appdb.* TO 'app_write';
GRANT 'app_read' TO 'user1'@'localhost';
```

### 主从复制

```sql
-- 主库
CREATE USER 'repl'@'%' IDENTIFIED BY 'repl-pass';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';

-- 从库
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='master_host', SOURCE_USER='repl', SOURCE_PASSWORD='repl-pass',
  SOURCE_AUTO_POSITION = 1;           -- GTID方式（推荐）
START REPLICA;
SHOW REPLICA STATUS\G                 -- 确认 IO/SQL 线程为 Yes
```

### 维护

```sql
ANALYZE TABLE users;                          -- 刷新优化器统计
OPTIMIZE TABLE users;                         -- 碎片整理（InnoDB 等同 ALTER TABLE ... FORCE）
CHECK TABLE users QUICK;                      -- 快速完整性检查

-- InnoDB 自动统计更新（无需手动 ANALYZE）
SET GLOBAL innodb_stats_auto_recalc = ON;

-- 每日维护脚本
mysql -e "CHECK TABLE appdb.users QUICK;"
mysql -e "ANALYZE LOCAL TABLE appdb.users;"
```

## PostgreSQL 16/17

> **来源**: [PostgreSQL 17 官方文档](https://www.postgresql.org/docs/17/)

### 安装

```bash
# RHEL/Fedora
dnf install postgresql-server
postgresql-setup --initdb
# 允许远程连接（生产环境应限定 IP）
echo "listen_addresses = '*'" >> /var/lib/pgsql/data/postgresql.conf
echo "host all all 0.0.0.0/0 scram-sha-256" >> /var/lib/pgsql/data/pg_hba.conf
systemctl enable --now postgresql.service

# Docker
docker run --name pg -d -p 5432:5432 -e POSTGRES_PASSWORD=pw postgres:17
```

> 💡 **关键配置调优** (`postgresql.conf`)：
> ```ini
> shared_buffers = 4GB                   # 物理内存的 25%
> effective_cache_size = 12GB            # 物理内存的 75%
> work_mem = 64MB                        # 单操作内存（复杂查询可会话级调大）
> maintenance_work_mem = 1GB             # VACUUM/CREATE INDEX 等维护操作内存
> random_page_cost = 1.1                 # SSD 环境设为 1.0-1.5
> ```

### psql CLI

```bash
psql -h host -p 5432 -U user -d db
psql -c "SELECT 1"                         # 执行单条SQL
psql -f script.sql -1                      # 执行脚本（单事务）
psql -t -A -c "SELECT version();"          # 纯文本输出（脚本用）
psql --csv -c "SELECT * FROM t;"           # CSV输出
```

**常用元命令**: `\l`(列库) `\dt`(列表) `\d name`(查看结构) `\di`(列索引) `\du`(列角色) `\x`(扩展显示) `\timing`(显示执行时间) `\conninfo`(当前连接信息) `\copy`(客户端导入导出) `\c`(重连)

### CRUD + RETURNING

```sql
INSERT INTO users (name) VALUES ('Alice') RETURNING *;

DELETE FROM tasks WHERE status = 'DONE' RETURNING *;

-- WITH 链式操作
WITH upd AS (
  UPDATE employees SET sales_count = sales_count + 1
  WHERE id = (SELECT sales_person FROM accounts WHERE name = 'Acme')
  RETURNING *
)
INSERT INTO employees_log SELECT *, current_timestamp FROM upd;
```

### 索引

```sql
CREATE INDEX idx ON t(col);                                    -- B-tree（默认）
CREATE INDEX gin_idx ON docs USING GIN (locations);            -- GIN（数组/JSON/全文）
CREATE INDEX gist_idx ON points USING gist (box(location));    -- GiST（几何/范围）
CREATE INDEX brin_idx ON logs USING BRIN (created_at);         -- BRIN（超大表）
CREATE INDEX partial_idx ON orders (created_at) WHERE status = 'OPEN';  -- 部分索引

-- 并发创建（不阻塞写入，但可能留 INVALID 索引）
CREATE INDEX CONCURRENTLY idx ON t(col);
```

### 查询优化

```sql
-- 查看实际执行计划
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;

-- 在事务中无副作用地分析DML
BEGIN;
EXPLAIN ANALYZE UPDATE ...;
ROLLBACK;
```

**pg_stat_statements** — 必须预加载的模块：
```ini
# postgresql.conf
shared_preload_libraries = 'pg_stat_statements'
```
```sql
CREATE EXTENSION pg_stat_statements;

-- 最慢的查询
SELECT query, calls, total_exec_time, rows,
       100.0 * shared_blks_hit / nullif(shared_blks_hit + shared_blks_read, 0) AS hit_pct
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5;
```

**auto_explain** — 自动记录慢查询执行计划：
```ini
session_preload_libraries = 'auto_explain'
auto_explain.log_min_duration = '3s'
auto_explain.log_analyze = on
```

### 备份与恢复

```bash
# 逻辑备份
pg_dump dbname > dumpfile                    # 纯SQL
pg_dump -Fc dbname > db.dump                 # 自定义格式（可选择性恢复）
pg_dump -Fd -j 8 -f backup_dir dbname        # 目录格式，并行

# 恢复
pg_restore -d dbname db.dump
psql -X dbname < dumpfile                    # 纯SQL恢复

# PITR 配置（WAL归档）
# postgresql.conf:
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /path/to/archive/%f && cp %p /path/to/archive/%f'
```

**时间点恢复**：
```ini
# recovery 配置
restore_command = 'cp /path/to/archive/%f %p'
recovery_target_time = '2026-08-03 10:30:00'
```
创建 `recovery.signal` 文件 → 启动PostgreSQL → 自动恢复到指定时间点。

### 维护


## MongoDB 7.x/8.x

> **来源**: [MongoDB Manual v8.0](https://www.mongodb.com/docs/v8.0/)

### 安装与连接

```bash
# Docker
docker run --name mongo -d -p 27017:27017 mongo:8.0
docker exec -it mongo mongosh
```

### CRUD

```javascript
// 插入
db.users.insertOne({ name: "Alice", age: 30 })
db.users.insertMany([{ name: "Bob" }, { name: "Cara" }], { ordered: false })

// 查询（filter + projection + sort + limit）
db.users.find({ name: "Alice" }, { _id: 0, name: 1, age: 1 })
db.orders.find({ status: "A" }).sort({ qty: -1 }).limit(10)

// $or 过滤器
db.movies.find({ $or: [{ runtime: { $gt: 1000 } }, { year: { $lt: 1910 } }] })

// 更新
db.inventory.updateOne({ item: "paper" }, { $set: { "size.uom": "cm", status: "P" } })
db.inventory.updateMany({ qty: { $lt: 50 } }, { $set: { status: "P" } }, { upsert: true })

// 删除
db.inventory.deleteOne({ status: "D" })
db.inventory.deleteMany({ status: "D" })
```

### 聚合管道

```javascript
db.movies.aggregate([
  { $match: { "directors": { $exists: true, $ne: null } } },
  { $unwind: "$directors" },
  { $group: { _id: "$directors", movieCount: { $sum: 1 } } },
  { $sort: { movieCount: -1 } },
  { $limit: 3 }
])

// $lookup（关联查询）+ $merge（输出到集合）
db.orders.aggregate([
  { $lookup: { from: "products", localField: "pid", foreignField: "_id", as: "product" } },
  { $unwind: "$product" },
  { $merge: { into: "order_details", whenMatched: "merge", whenNotMatched: "insert" } }
])
```

### 索引

```javascript
db.orders.createIndex({ item: 1, quantity: 1 })                           // 复合索引
db.orders.createIndex({ item: 1, price: 1 }, { partialFilterExpression: { price: { $gte: 10 } } })  // 部分索引
db.articles.createIndex({ subject: "text" })                              // 全文索引
db.restaurants.createIndex({ location: "2dsphere" })                      // 地理空间索引

// TTL 索引（自动过期，3600秒后删除）
db.eventlog.createIndex({ "lastModifiedDate": 1 }, { expireAfterSeconds: 3600 })
```

**TTL 注意事项**：单字段索引 / 后台线程每60秒运行一次 / 只在主节点运行 / 删除非并发（单线程）。

```bash
sudo apt-get update && sudo apt-get install redis-stack-server

```

### 数据结构与命令

```bash
# String（字符串）
SET key "value" EX 100 NX          # 仅当不存在时设置，100秒过期
GET key                            # "value"
INCR counter                       # 原子自增
EXPIRE key 60                      # 设置过期时间

# Hash（哈希）
HSET user:1000 name "Alice" age 30
HGET user:1000 name                # "Alice"
HGETALL user:1000                  # 获取所有字段
HINCRBY user:1000 age 1            # 原子递增字段

# List（列表）
RPUSH queue "job1" "job2"          # 尾部追加
LPOP queue                         # 头部弹出
BLPOP queue 5                      # 阻塞弹出，5秒超时（消息队列模式）

# Set（集合）
SADD tags:rust "async" "systems"
SADD tags:web  "async" "http"
SINTER tags:rust tags:web          # 交集 → "async"
SUNION tags:rust tags:web          # 并集

# Sorted Set（有序集合）
```

### 常见陷阱

1. **`PRAGMA foreign_keys` 默认 OFF** — 每个连接都要手动 `PRAGMA foreign_keys=ON;`
2. **`.tables` 列出表和视图** — 不含索引，可能把视图误当表
3. **WAL 模式不能单独复制 .db 文件** — 必须先 checkpoint 或用 `.backup`/`VACUUM INTO`
4. **WAL 模式有数据竞争 bug** — 升级到 ≥3.51.3（已在 2026-03-13 修复）
5. **`LIKE` 默认 ASCII 大小写** — 非 BINARY 排序规则列上可能无法使用索引
6. **INTEGER PRIMARY KEY 才自动自增** — 其他 `PRIMARY KEY` 不自动生成值
7. **未知 PRAGMA 静默忽略** — `PRAGMA foreign_key=ON`（少了 s）不会报错也不会生效

## 索引优化实战

> 索引是数据库性能的命门。用得好，查询飞起；用得不好，写入拖垮。本章深入 B+Tree 原理、联合索引设计、索引失效场景及生产级设计决策树。

🎯 **软考考点**：数据库系统章节中，索引结构（B+树）、查询优化、范式与反范式设计是上午题的高频考点（5-7分）。

### B+Tree vs Hash 索引原理图解

```
════════════════════════════════════════════════════════
            B+Tree 索引结构 (MySQL InnoDB 默认)
════════════════════════════════════════════════════════

    非叶子节点 (只存 key + 子节点指针, 不存数据)
           ┌─────────┐
           │ [50|100]│         ← 根节点 (Root Page)
           └────┬────┘
        ┌───────┼───────┐
   ┌────┴───┐ ┌─┴────┐ ┌┴──────────┐
   │[10|30] │ │[70]  │ │[150|200]  │  ← 内部节点 (Internal Pages)
   └──┬──┬──┘ └──┬───┘ └──┬───┬────┘
  ┌───┘  └───┐   │       │   └──────┐
  ▼          ▼   ▼       ▼          ▼
┌──────────┐ ┌──────────┐ ┌──────────┐
│叶子节点层│ │叶子节点层│ │叶子节点层│  ← 叶节点 (Leaf Pages)
│ 数据+key │→│ 数据+key │→│ 数据+key │  双向链表连接 ← ★范围查询关键
└──────────┘ └──────────┘ └──────────┘

════════════════════════════════════════════════════════
            Hash 索引结构 (Memory 引擎 / PG Hash)
════════════════════════════════════════════════════════

   key     → hash(key) → bucket
   ─────────────────────────────
   "Alice"    → 0x3A2F  ─→ ┌─────────────────┐
                            │ "Alice" → data   │
   "Bob"      → 0x7C1D  ─→ │ "Bob"   → data   │
                            └─────────────────┘

   特点: O(1) 精确查找, 无序存储, 不支持范围查询
```

| 特性 | B+Tree | Hash |
|------|--------|------|
| **精确查询 `=`** | O(log n) | O(1) ★更快 |
| **范围查询 `<`, `>`, `BETWEEN`** | ✅ 叶节点链表遍历 | ❌ 不支持 |
| **前缀查询 `LIKE 'abc%'`** | ✅ | ❌ |
| **排序 `ORDER BY`** | ✅ 天然有序 | ❌ 无序 |
| **GROUP BY / DISTINCT** | ✅ 可利用有序性 | ❌ |
| **磁盘I/O** | 按页(16KB)读取, 局部性好 | 单条随机, 局部性差 |
| **适用场景** | 90% 通用场景 | 内存表、等值查询专用 |

**InnoDB 的 Adaptive Hash Index (AHI)**：InnoDB 会在 Buffer Pool 中自动为频繁等值访问的 B+Tree 页面构建 Hash 索引，无需手动干预。`SHOW ENGINE INNODB STATUS\G` 可查看 AHI 命中率。

### 覆盖索引 (Covering Index)

> **💡 生活类比**：想象一本字典需要查找"苹果"的定义。普通索引告诉你去第 352 页（回表查），覆盖索引直接把第 352 页的字义也写在索引里——你不需要再翻那一页。

```sql
-- 普通索引：需要回表
CREATE INDEX idx_name ON users(name);
SELECT id, name, email FROM users WHERE name = 'Alice';
-- 流程: idx_name 找到主键 id → 回表聚簇索引取 email → 返回

-- 覆盖索引：不回表
CREATE INDEX idx_name_email ON users(name, email);
SELECT id, name, email FROM users WHERE name = 'Alice';
-- 流程: idx_name_email 直接拿到 id, name, email → 返回 ✓
-- EXPLAIN Extra 显示: Using index (覆盖索引标志!)
```

**验证是否使用覆盖索引**：

```sql
EXPLAIN SELECT name, email FROM users WHERE name = 'Alice';
-- 看 Extra 列: Using index  =  覆盖索引生效 (Good!)
-- 看 Extra 列: NULL 或 Using where  =  回表查询
```

> ⚠️ **覆盖索引的代价**：索引变大了，写入更慢。别把所有列都塞进索引——GitHub 曾经有个著名的 PR，给 `users` 表建了个 50 列的联合索引。

### 联合索引与最左前缀原则

> 🎯 **软考考点**：上午题常考"给定 SQL 和索引 (a,b,c)，判断哪些查询能用到索引"。

```sql
-- 创建联合索引 (a, b, c)
CREATE INDEX idx_abc ON orders(status, user_id, created_at);
```

| 查询条件 | 是否用到 idx_abc | 解释 |
|----------|:---:|------|
| `WHERE status = 'paid'` | ✅ | 最左列 a (关键段) |
| `WHERE status = 'paid' AND user_id = 1` | ✅ | a + b (关键段) |
| `WHERE status = 'paid' AND user_id = 1 AND created_at > '2026-01-01'` | ✅ | a + b + c (完全关键段) |
| `WHERE user_id = 1` | ❌ | 跳过 a，索引失效 |
| `WHERE user_id = 1 AND created_at > '2026-01-01'` | ❌ | 跳过 a，索引失效 |
| `WHERE status = 'paid' AND created_at > '2026-01-01'` | ⚠️ | 只用 a (key_len=status长度)，c 因跳过 b 而失效 |
| `WHERE status > 'paid'` | ✅ | 范围查询 a，b/c 后续失效 |
| `WHERE status = 'paid' ORDER BY user_id` | ✅ | 索引有序（无 filesort） |
| `WHERE status = 'paid' ORDER BY created_at` | ⚠️ | a 过滤, c 排序跳过 b → filesort |
| `WHERE status = 'paid' AND user_id = 1 ORDER BY created_at` | ✅ | a+b 过滤, c 排序，完美利用 |

**EXPLAIN 验证**：

```sql
EXPLAIN SELECT * FROM orders
WHERE status = 'paid' AND user_id = 1 AND created_at > '2026-01-01';

-- 关键输出解读:
-- key: idx_abc           ← 使用了联合索引
-- key_len: 96            ← 实际用到的索引长度 (status 4B + user_id 4B ≡ 8B)
-- type: range            ← 范围扫描 (比 ref 差, 比 ALL 好得多)
-- Extra: Using index condition  ← ICP 优化 (Index Condition Pushdown)
```

> 💡 **索引设计口诀**：「等值在前，范围在后；高频在前，低频在后。」

🎯 **软考真题链接**：给定关系模式 R(A,B,C,D) 和查询 `SELECT * FROM R WHERE A=1 AND B>2 AND C=3`，应建立什么索引？→ `(A,C)` 或 `(A,C,B)`，A 必须最左，C 等值优先于 B 的范围。

### 索引失效场景汇总

> ⚠️ **写 SQL 就一条原则**：让索引列保持"裸"的——不加函数、不参与运算、不隐式转换。

```sql
-- ❌ 场景1: 在索引列上使用函数
SELECT * FROM users WHERE YEAR(created_at) = 2026;
-- ✅ 改写:
SELECT * FROM users WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';

-- ❌ 场景2: 隐式类型转换 (MySQL 自动 CAST)
-- phone 是 VARCHAR, 但传了 INT
SELECT * FROM users WHERE phone = 13800138000;
-- MySQL 实际执行: WHERE CAST(phone AS SIGNED) = 13800138000  ← 函数包裹索引列!
-- ✅ 改写:
SELECT * FROM users WHERE phone = '13800138000';

-- ❌ 场景3: LIKE 以 % 开头
SELECT * FROM products WHERE name LIKE '%phone%';   -- 全表扫描
-- ✅ 改写:
SELECT * FROM products WHERE name LIKE 'phone%';     -- 范围扫描
-- 如果必须前后都要 %，考虑全文索引 (FULLTEXT)

-- ❌ 场景4: OR 条件中一侧无索引
SELECT * FROM orders WHERE user_id = 1 OR status = 'paid';
-- user_id 有索引, status 无 → 可能全表扫描
-- ✅ 改写: 用 UNION ALL
SELECT * FROM orders WHERE user_id = 1
UNION ALL
SELECT * FROM orders WHERE status = 'paid' AND user_id != 1;

-- ❌ 场景5: NOT、!=、<> 不等值判断 (大部分情况走全表)
SELECT * FROM users WHERE status != 'deleted';  -- 通常不走索引
-- ✅ 如果 status 只有几个值, 用 IN:
SELECT * FROM users WHERE status IN ('active', 'pending', 'suspended');

-- ❌ 场景6: IS NULL / IS NOT NULL (取决于 NULL 比例)
SELECT * FROM users WHERE deleted_at IS NOT NULL;
-- 优化器评估: 如果 NOT NULL 行数 > ~20%, 可能选择全表扫描

-- ❌ 场景7: 联合索引不满足最左前缀
-- 索引 (a, b, c), 查询 WHERE b=1 AND c=2  → 索引失效

-- ❌ 场景8: 索引列参与运算
SELECT * FROM orders WHERE amount + tax > 100;  -- 运算在列上
-- ✅ 改写:
SELECT * FROM orders WHERE amount > 100 - tax;

-- ❌ 场景9: 使用了 != ALL / NOT IN 子查询 (可能走全表)
-- ❌ 场景10: 数据量太小 (优化器判定全表更快)
-- ❌ 场景11: MySQL 选错索引 (用 FORCE INDEX 纠正)
SELECT * FROM orders FORCE INDEX(idx_created) WHERE created_at > '2026-01-01';
```

### 索引设计决策树

```
                        新查询需要优化?
                              │
                    ┌─────────┴─────────┐
                    │ 先 EXPLAIN 看现状  │
                    └─────────┬─────────┘
                              │
                    type=ALL / rows 巨大?
                              │
                      ┌───────┴───────┐
                      │  YES           │ NO → 当前索引OK，结束
                      └───────┬───────┘
                              │
                    WHERE 条件有等值查询?
                      ┌───────┴───────┐
                      │  YES           │ NO → 考虑覆盖索引或物化视图
                      └───────┬───────┘
                              │
                    多个 AND 条件?
                      ┌───────┴───────┐
                      │  YES           │ NO → 单列索引
                      └───────┬───────┘

                    有范围查询 (>, <, BETWEEN) ?
                      ┌───────┴──────────────┐
                      │  YES                   │ NO
                      ▼                        ▼
              联合索引: (等值列..., 范围列)    联合索引: (高频等值列..., 低频等值列)

                      ┌───────┴──────────────┐

                      └───────────────────────┘
```

> ⚠️ **生产禁忌**：
> - 不要学网上教程给每个 `WHERE` 列都建单列索引——MySQL 通常只用其中一个
> - 索引不是越多越好：每个索引拖慢 INSERT/UPDATE/DELETE 约 5-15%
> - 单表索引数控制在 **5-8 个**以内
> - 用 `sys.schema_unused_indexes` (MySQL) 或 `pg_stat_user_indexes` (PG) 定期清理无用索引

**索引监控命令速查**：

```sql
-- MySQL: 未使用索引
SELECT * FROM sys.schema_unused_indexes
WHERE object_schema NOT IN ('mysql', 'sys', 'performance_schema');

-- MySQL: 冗余索引 (A被AB覆盖)

-- PostgreSQL: 索引使用统计

       idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;  -- 扫描最少的 = 可能用不上
```

## 事务与隔离级别详解

> 事务是数据库区别于文件系统的核心能力。本章深入 ACID 原理、隔离级别的实际表现、以及 MySQL/PostgreSQL 的 MVCC 实现。

🎯 **软考考点**：事务特性（ACID）、封锁协议、两段锁协议、死锁是上午题高频考点。

### ACID 原理深入

```
┌─────────────────────────────────────────────────────────────────┐
│                        ACID 四特性                              │
├──────────┬──────────────────────────────────────────────────────┤
│ A 原子性  │ 事务要么全部成功，要么全部回滚                         │
│ Atomicity│ 实现: Undo Log (回滚段) — 记录修改前的旧值              │
│          │ 类比: 银行转账 — 扣A和加B必须同时成功或同时失败          │
│          │ 破坏场景: 事务执行一半，数据库崩溃                      │
├──────────┼──────────────────────────────────────────────────────┤
│ C 一致性  │ 事务前后，数据必须满足所有约束（外键、唯一、CHECK）       │
│Consistency│ 实现: 约束检查 + 应用层逻辑                           │
│          │ 类比: 无论怎么转账, 银行总资产不变                       │
│          │ 破坏场景: 触发器/外键设置不当导致数据矛盾                  │
├──────────┼──────────────────────────────────────────────────────┤
│ I 隔离性  │ 并发事务互不干扰 (程度由隔离级别决定)                   │
│ Isolation │ 实现: 锁 (Lock) + MVCC (多版本并发控制)               │
│          │ 类比: 两个人同时编辑同一个文档的不同段落, 互不影响          │
│          │ 破坏场景: 脏读、不可重复读、幻读                        │
├──────────┼──────────────────────────────────────────────────────┤
│ D 持久性  │ 事务提交后，数据永久保存，即使系统崩溃                   │
│ Durability│ 实现: Redo Log (WAL) — 先写日志再写数据               │
│          │ 类比: 签字画押后无法抵赖                               │
│          │ 破坏场景: 提交后立即断电，Redo Log 未刷盘                │
└──────────┴──────────────────────────────────────────────────────┘
```

### 四种隔离级别与并发异常

> **💡 生活类比**：你和同事编辑共享文档——
> - **READ UNCOMMITTED** = 同事还在打字你就看到了（可能他马上删除）→ 脏读
> - **READ COMMITTED** = 只有同事按保存(Ctrl+S)你才看到 → 不可重复读：你读两次之间他改了
> - **REPEATABLE READ** = 你打开时拍了快照，整个编辑过程看到的是打开时的版本 → 幻读：你筛选"所有红色段落"，编辑过程中同事新增了一个红色段落
> - **SERIALIZABLE** = 只能一个人编辑，其他人排队

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现方式 | 默认数据库 |
|----------|:---:|:---:|:---:|----------|-----------|
| **READ UNCOMMITTED** | ✅ 会 | ✅ 会 | ✅ 会 | 不加锁, 读最新版本 | — |
| **READ COMMITTED** | ❌ | ✅ 会 | ✅ 会 | 每次读最新已提交版本 | PG, SQL Server, Oracle |
| **REPEATABLE READ** | ❌ | ❌ | ⚠️ 部分 | 事务开始时的快照 | **MySQL InnoDB** |
| **SERIALIZABLE** | ❌ | ❌ | ❌ | 串行化锁/MVCC检测 | — |

> ⚠️ **MySQL 的 REPEATABLE READ 也不会有幻读**（通过 Gap Lock/Next-Key Lock），这是 MySQL 的独特之处。所以 MySQL 的 RR 实际上已经达到了和 SERIALIZABLE 相同的效果。

### 四种异常现象 SQL 演示

准备环境（两个会话窗口）：

```sql
-- 初始化
CREATE TABLE accounts (
  id INT PRIMARY KEY,
  name VARCHAR(50),
  balance DECIMAL(10,2)
);
INSERT INTO accounts VALUES (1, 'Alice', 1000.00);
INSERT INTO accounts VALUES (2, 'Bob', 500.00);
```

**1. 脏读 (Dirty Read)** — 读到未提交的数据

```sql
-- 会话A: READ UNCOMMITTED                   -- 会话B
SET SESSION TRANSACTION ISOLATION LEVEL
  READ UNCOMMITTED;
START TRANSACTION;
                                           START TRANSACTION;
                                           UPDATE accounts SET balance = 9999
                                           WHERE id = 1;
                                           -- B 还没 COMMIT!
SELECT balance FROM accounts WHERE id = 1;
-- 结果: 9999  ← 脏读! B 可能回滚
```

**2. 不可重复读 (Non-Repeatable Read)** — 同一事务两次读取结果不同

```sql
-- 会话A: READ COMMITTED                      -- 会话B
START TRANSACTION;
SELECT balance FROM accounts WHERE id = 1;
-- 结果: 1000
                                           START TRANSACTION;
                                           UPDATE accounts SET balance = 8888
                                           WHERE id = 1;
                                           COMMIT;  -- B 提交了
SELECT balance FROM accounts WHERE id = 1;
-- 结果: 8888  ← 不可重复读! 和第一次不一样
COMMIT;
```

**3. 幻读 (Phantom Read)** — 同一条件两次查询，第二次多出/少了行

```sql
-- 会话A: READ COMMITTED                      -- 会话B
START TRANSACTION;
SELECT * FROM accounts WHERE balance > 500;
-- 结果: [Alice (1000)]
                                           START TRANSACTION;
                                           INSERT INTO accounts VALUES (3, 'Cara', 2000);
                                           COMMIT;
SELECT * FROM accounts WHERE balance > 500;
-- 结果: [Alice (1000), Cara (2000)]
-- ← 幻读! 多了一行
COMMIT;
```

**MySQL REPEATABLE READ 如何消除幻读**：

```sql
-- MySQL InnoDB 默认 RR
-- 会话A                                        -- 会话B
START TRANSACTION;
SELECT * FROM accounts WHERE balance > 500;
-- [Alice (1000)]
                                           START TRANSACTION;
                                           INSERT INTO accounts VALUES (3, 'Cara', 2000);
                                           -- 被阻塞! InnoDB 加了 Gap Lock
                                           -- 锁住了 (500, +∞) 这个间隙
```

### MVCC 原理

> MVCC (Multi-Version Concurrency Control) 是实现非锁定读的核心技术。原理：**写不阻塞读，读不阻塞写**——每个事务看到的是数据的某个快照版本。

#### MySQL InnoDB MVCC

```
每条行记录隐藏三列:
┌──────────────────────────────────────────────────────────┐
│  DB_TRX_ID (6B)  │  DB_ROLL_PTR (7B)  │  DB_ROW_ID (6B) │
│  最后修改的事务ID  │  指向 Undo Log 的指针 │  隐藏主键(无PK时) │
└──────────────────────────────────────────────────────────┘

Undo Log 版本链 (回滚段):
  ┌─────────────────────────────────────────────────────┐
  │  当前值: balance=200 (trx_id=10)                     │
  │       │                                              │
  │       ▼  DB_ROLL_PTR 指向                            │
  │  Undo: balance=150 (trx_id=8)                        │
  │       │                                              │
  │       ▼                                              │
  │  Undo: balance=100 (trx_id=5)                        │
  │       │                                              │
  │       ▼                                              │
  │  Undo: (初始值, 无前版本)                               │
  └─────────────────────────────────────────────────────┘

ReadView (快照) 判断可见性:
  当前活跃事务列表: [8, 9]
  trx_id=10 → 在活跃列表之后 → 不可见 (未提交)
  trx_id=8  → 在活跃列表中   → 不可见 (当前事务未提交的修改)
  trx_id=5  → 不在活跃列表    → 可见 ✓ (已提交)
```

**READ COMMITTED vs REPEATABLE READ 的 ReadView 区别**：

- **RC**：每次 SELECT 都创建新的 ReadView → 能看到其他事务的提交 → 不可重复读
- **RR**：只在第一次 SELECT 时创建 ReadView，整个事务复用 → 看不到其他事务的提交 → 可重复读

#### PostgreSQL MVCC

```sql
-- PG 的 MVCC 更直接: 每行存 xmin/xmax
-- xmin: 插入该行的事务ID
-- xmax: 删除/更新该行的事务ID (0 表示当前版本有效)

-- 查询可见性规则:
-- 可见条件: xmin < 当前事务ID AND (xmax = 0 OR xmax > 当前事务ID)

-- 查看行的隐藏字段
SELECT xmin, xmax, * FROM accounts;

-- PG 的 VACUUM 就是清理 xmax < 所有活跃事务最小ID 的死行
VACUUM accounts;  -- 标记死行为可重用空间
```

| 对比维度 | MySQL InnoDB | PostgreSQL |
|----------|-------------|------------|
| 旧版本存储 | Undo Log (回滚段) | 数据页内 (新旧同存) |
| 清理机制 | Purge Thread (后台自动) | VACUUM (需关注膨胀) |
| 事务ID回卷 | 有风险, 但 8.0 自动处理 | **XID Wraparound** 风险, 必须定期 VACUUM |
| 回滚速度 | 快 (Undo 日志顺序回滚) | 相对慢 (需逐行标记) |
| 版本膨胀 | 较轻 | 必须关注 (pg_stat_user_tables.n_dead_tup) |

### 死锁检测与解决

> **💡 生活类比**：两个人过独木桥——A 在桥这头，B 在桥那头，谁都不肯退。数据库死锁同理：A 锁了行1想锁行2，B 锁了行2想锁行1。

```sql
-- 制造死锁演示
-- 会话A:                                       -- 会话B:
START TRANSACTION;                              START TRANSACTION;
UPDATE accounts SET balance=100 WHERE id=1;     UPDATE accounts SET balance=200 WHERE id=2;
-- 锁住 id=1                                    -- 锁住 id=2
UPDATE accounts SET balance=100 WHERE id=2;     UPDATE accounts SET balance=200 WHERE id=1;
-- 等待 id=2 的锁 (被B持有)                      -- 等待 id=1 的锁 (被A持有)
-- ...                                          -- ...
-- 死锁! InnoDB 检测到后回滚其中一个事务            -- 或被回滚, 或成功继续
```

**死锁日志解读**：

```sql
-- MySQL 查看最近一次死锁
SHOW ENGINE INNODB STATUS\G
-- 搜索 "LATEST DETECTED DEADLOCK" 部分

-- PostgreSQL 查看死锁
SELECT * FROM pg_stat_activity WHERE wait_event_type = 'Lock';

-- SQL Server 死锁图
-- 开启跟踪标志 1222 将死锁信息写入错误日志
DBCC TRACEON(1222, -1);
```

**避免死锁的策略**：

```sql
-- 1. 固定加锁顺序 (最重要!)
-- ❌ 事务A: 先锁 id=1 再锁 id=2
-- ❌ 事务B: 先锁 id=2 再锁 id=1  → 死锁
-- ✅ 所有事务都按 id 升序加锁

-- 2. 缩短事务 (锁持有时间越短越好)
-- ❌ 在事务中做 RPC 调用、发邮件
-- ✅ 事务只包含数据库操作，业务逻辑放外面

-- 3. 使用 SELECT ... FOR UPDATE NOWAIT (PG) / SKIP LOCKED
START TRANSACTION;
SELECT * FROM tasks WHERE status = 'pending'
  ORDER BY id LIMIT 1
  FOR UPDATE SKIP LOCKED;  -- 跳过已锁定的行, 不等待!
-- 处理该任务...
COMMIT;

-- 4. 降低隔离级别 (如果业务允许)
-- RR → RC 可以减少间隙锁带来的死锁概率

-- 5. 索引优化 (减少锁范围)
-- 无索引: WHERE name='Alice' 锁全表 (所有行+间隙)
-- 有索引: WHERE name='Alice' 只锁匹配行
```

🎯 **软考真题链接**：两段锁协议（2PL）— 事务分两个阶段：扩展阶段（只加锁不解锁）和收缩阶段（只解锁不加锁）。遵循 2PL 可保证可串行化调度。

## SQL 性能优化

> 慢查询是数据库运维的第一大敌。本章从 EXPLAIN 解读、N+1 问题、慢查询日志、分页优化到 JOIN 策略，覆盖 80% 的生产性能问题。

🎯 **软考考点**：查询优化（等价变换、代数优化）是上午题必考项。

### EXPLAIN / EXPLAIN ANALYZE 深度解读

```sql
-- MySQL EXPLAIN
EXPLAIN SELECT u.name, o.total
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.created_at > '2026-01-01'
ORDER BY o.created_at DESC
LIMIT 10;

-- 输出解读:
+----+-------------+-------+-------+---------------+---------+---------+------+------+-------------+
| id | select_type | table | type  | possible_keys | key     | key_len | ref  | rows | Extra       |
+----+-------------+-------+-------+---------------+---------+---------+------+------+-------------+
|  1 | SIMPLE      | u     | range | idx_created   | idx_created | 5     | NULL | 1000 | Using where; Using temporary; Using filesort |
|  1 | SIMPLE      | o     | ref   | idx_user_id   | idx_user_id | 4     | u.id |   10 | NULL        |
+----+-------------+-------+-------+---------------+---------+---------+------+------+-------------+
```

**EXPLAIN 关键列速查表**：

| 列 | 含义 | 重点关注 |
|----|------|----------|
| **id** | 执行顺序 (大→小) | 多个 SELECT 时区分子查询 |
| **select_type** | 查询类型 | SIMPLE > SUBQUERY > DERIVED > UNION |
| **type** | 访问类型 ★最重要★ | `ALL`(全表) → `index` → `range` → `ref` → `eq_ref` → `const/system`(最优) |
| **possible_keys** | 候选索引 | 空 → WHERE 列上无索引 |
| **key** | 实际使用的索引 | 与 possible_keys 不同 = 优化器选错了 |
| **key_len** | 索引使用长度 | 联合索引: 可判断用了几个列 |
| **rows** | 预估扫描行数 | 越大越慢，对比实际返回行数 |
| **Extra** | 额外信息 ★重要★ | 见下表 |

**Extra 列红灯警报**：

| Extra 显示 | 严重程度 | 解释 | 解决 |
|------------|:---:|------|------|
| `Using filesort` | 🔴 高 | 额外排序，无法利用索引顺序 | 将 ORDER BY 列加入索引 |
| `Using temporary` | 🔴 高 | 使用临时表 (GROUP BY/DISTINCT) | 优化 GROUP BY 列索引 |
| `Using where` | 🟡 中 | 回表后过滤 | 考虑覆盖索引 |
| `Using index` | 🟢 优 | 覆盖索引，不回表 | 保持! |
| `Using index condition` | 🟢 优 | ICP 下推 (Server层过滤下推到引擎层) | 保持! |
| `Select tables optimized away` | 🟢 最优 | 只读索引统计信息即返回 (COUNT/MIN/MAX) | 保持! |

**PostgreSQL EXPLAIN ANALYZE** — 更强大，显示实际执行时间：

```sql
EXPLAIN (ANALYZE, BUFFERS, TIMING) SELECT ...;

-- 示例输出:
-- Seq Scan on users  (cost=0.00..35.50 rows=1000 width=40)
--   (actual time=0.015..2.350 rows=1000 loops=1)
--   Filter: (created_at > '2026-01-01'::date)

--   Buffers: shared hit=85          ← Buffer Pool 命中 85 页

-- actual time 远大于 cost 估算 → 统计信息过期 → ANALYZE

```

### N+1 查询问题及解决方案

> **💡 生活类比**：你想列出所有部门和每个部门的员工。N+1 的做法是：先查所有部门（1次），然后对每个部门单独查员工（N次）。就像去餐厅点菜，先问"有什么菜"，然后对每道菜单独问"这道菜用什么食材"。

```sql
-- ❌ N+1 反模式
-- 1 次查询
SELECT id, name FROM departments;
-- 结果: [1, '技术部'], [2, '销售部'], [3, '市场部'], ... [100, '行政部']

-- N 次查询 (每行一次!)
SELECT * FROM employees WHERE dept_id = 1;
SELECT * FROM employees WHERE dept_id = 2;
SELECT * FROM employees WHERE dept_id = 3;
...
SELECT * FROM employees WHERE dept_id = 100;
-- 总计: 1 + 100 = 101 次查询!

-- ✅ 方案1: JOIN (一次搞定)
SELECT d.name AS dept, e.name AS emp
FROM departments d
LEFT JOIN employees e ON d.id = e.dept_id;

-- ✅ 方案2: IN 批量查询 (应用层拼接)
-- 步骤1: 查出所有部门ID
SELECT id FROM departments WHERE status = 'active';
-- 步骤2: 用 IN 一次查出所有员工
SELECT * FROM employees WHERE dept_id IN (1, 2, 3, ..., 100);

-- ✅ 方案3: 子查询 / EXISTS
SELECT d.*, (
  SELECT JSON_ARRAYAGG(JSON_OBJECT('id', id, 'name', name))
  FROM employees WHERE dept_id = d.id
) AS employees
FROM departments d;

-- ✅ 方案4 (ORM): Django 的 select_related / prefetch_related
-- Django QuerySet:
Departments.objects.prefetch_related('employees').all()
-- SQLAlchemy:
session.query(Department).options(joinedload(Department.employees)).all()
```

**不同 ORM 的 N+1 预防机制**：

| ORM | JOIN 预加载 | 批量查询预加载 |
|-----|-----------|--------------|
| Django | `select_related()` (FK/OneToOne) | `prefetch_related()` (M2M/反向FK) |
| SQLAlchemy | `joinedload()` | `selectinload() / subqueryload()` |
| Rails ActiveRecord | `includes(:relation)` | 同 |
| Laravel Eloquent | `with('relation')` | 同 |
| Prisma | `include: { relation: true }` | — |

### 分页优化

> **💡 生活类比**：翻书有两种方式 — ①直接说"翻到第300页" ②说"从第1页开始，翻299次到第300页"。OFFSET 分页就是②，数据量越大越慢：数据库必须数完前299页再给你第300页的内容。

```sql
-- ❌ OFFSET 分页 (线性增长, 越往后越慢)
SELECT * FROM articles ORDER BY id LIMIT 20 OFFSET 1000000;
-- 数据库干了什么: 排序 → 数 1,000,000 行 → 跳过 → 返回 20 行
-- 时间: 可能超过 5 秒

-- ✅ 方案1: 游标分页 (Keyset Pagination) — 利用索引
SELECT * FROM articles WHERE id > 1000000 ORDER BY id LIMIT 20;
-- 数据库干了什么: 索引定位到 id=1000000 → 向后取 20 行 → 返回
-- 时间: < 1ms (走主键索引)

-- ✅ 方案2: 子查询定位 + JOIN (适用无自增ID的场景)
SELECT * FROM articles a
JOIN (SELECT id FROM articles ORDER BY created_at DESC LIMIT 20 OFFSET 1000000) tmp
ON a.id = tmp.id;
-- 子查询只取 id (覆盖索引), 避免全行排序

-- ✅ 方案3: 禁止深度翻页 (产品层面)
-- 百度/Google 搜索结果最多显示前 1000 条
-- LIMIT 1000 后直接给用户提示"请缩小搜索范围"
```

**游标分页的 API 设计**：

```json
// ❌ 传统分页
GET /api/articles?page=100&page_size=20

// ✅ 游标分页
GET /api/articles?cursor=eyJpZCI6MTAwMDAwfQ&limit=20&direction=next

// 响应中返回 next_cursor 和 prev_cursor
{
  "data": [...],
  "pagination": {
    "next_cursor": "eyJpZCI6MTAwMDIwfQ==",
    "has_more": true
  }
}
```

| 分页方式 | 优点 | 缺点 |
|----------|------|------|
| **OFFSET/LIMIT** | 实现简单, 支持跳页 | 大偏移量性能极差 O(n) |
| **游标 (Cursor)** | O(1) 恒定性能, 实时数据 | 不支持跳页, 需要索引 |
| **子查询 + JOIN** | 兼容传统 API, 性能大幅提升 | 需要覆盖索引 |
| **Elasticsearch search_after** | 深分页专用, 10,000+ 条 | 需要额外中间件 |

### JOIN 优化策略

```sql
-- Nested Loop Join (小表驱动大表原则)
-- 驱动表 (外层) 越小越好, 被驱动表 (内层) 必须有索引

-- ❌ 大表驱动
SELECT * FROM big_orders o    -- 1000万行 (驱动表)
JOIN small_users u ON o.user_id = u.id;  -- 1000万次 user_id 查找

-- ✅ 小表驱动
SELECT * FROM small_users u   -- 1000行 (驱动表)
JOIN big_orders o ON u.id = o.user_id;   -- 1000次 user_id 查找 (走索引)
```

**JOIN 算法对比**：

| 算法 | 适用场景 | MySQL | PostgreSQL |
|------|----------|:---:|:---:|
| **Nested Loop** | 小表 JOIN 大表 (驱动表小) | ✅ 默认 | ✅ |
| **Hash Join** | 两表都较大, 无合适索引 | ✅ 8.0.18+ | ✅ 默认 |
| **Merge Join** | 两表都按 JOIN 键排序 | ❌ | ✅ |
| **Block Nested Loop** | 无索引时的兜底 | ✅ 旧版 | — |

```sql
-- JOIN 优化检查清单:
-- 1. JOIN 列上建立索引 (第一优先级)
-- 2. 只 SELECT 需要的列 (避免 SELECT *)
-- 3. WHERE 条件尽可能早地过滤 (减少 JOIN 的行数)
-- 4. 小结果集做驱动表 (STRAIGHT_JOIN 强制驱动顺序)
-- 5. 拆分大 JOIN 为多个小查询 + 应用层拼接

-- 用 STRAIGHT_JOIN 强制执行顺序 (MySQL)
SELECT STRAIGHT_JOIN u.name, COUNT(o.id) AS order_count
FROM users u                         -- 强制 u 为驱动表
JOIN orders o ON u.id = o.user_id
WHERE u.status = 'active'
GROUP BY u.id;
```

🎯 **软考真题链接**：查询树优化 — 先选择后连接（把 σ 推到叶子节点），投影运算尽早做。等价变换规则：`σ_F1∧F2(E) ≡ σ_F1(σ_F2(E))`。

> 当单表突破 500 万行或单库 QPS 突破 1000 时，单机数据库到达瓶颈。本章覆盖拆分策略、分片键设计、中间件配置和数据一致性保障。

### 垂直拆分 vs 水平拆分

```
═══════════════════════════════════════════════════════
           垂直拆分 (Vertical Partitioning)
═══════════════════════════════════════════════════════

  原表: users (id, name, email, password_hash,
               avatar_url, bio, settings_json,
               created_at, updated_at, deleted_at)

  拆分为:

  ┌─ users_main ──────────┐   ┌─ users_profile ─────┐
  │ id, name, email        │   │ user_id, avatar_url, │
  │ password_hash,         │   │ bio, settings_json   │
  │ created_at, updated_at │   │                      │
  └────────────────────────┘   └──────────────────────┘
      ↑ 高频查询 (登录)            ↑ 低频查询 (个人页)

═══════════════════════════════════════════════════════
           水平拆分 (Horizontal Partitioning)
═══════════════════════════════════════════════════════

  原表: orders (2000万行)

  按 user_id % 4 拆分为:

  orders_0  → user_id % 4 = 0  (500万行)
  orders_1  → user_id % 4 = 1  (500万行)
  orders_2  → user_id % 4 = 2  (500万行)
  orders_3  → user_id % 4 = 3  (500万行)

  每个分片可部署在独立数据库实例上
```

| 拆分方式 | 原理 | 优点 | 缺点 | 适用场景 |
|----------|------|------|------|----------|
| **垂直拆分** | 按列拆表 | 减少行宽, 提高缓存效率 | 需要 JOIN 的列必须在同一库 | 宽表 (50+列), 冷热数据分离 |
| **水平拆分** | 按行拆表 | 无限扩展, 分散压力 | 跨分片查询复杂, 分布式事务 | 大表 (500万+), 高并发写入 |

### 分片键选择策略

> ⚠️ **分片键是最重要的设计决策，一旦上线几乎无法更改。**

```
分片键选择决策矩阵:

              ┌─ 数据分布均匀? ──────────────────────┐
              │   ✅ user_id/hash       ❌ gender      │
              │   ❌ create_time (时间倾斜)              │
              └───────────────────────────────────────┘
              ┌─ 查询模式匹配? ───────────────────────┐
              │   ✅ 大部分查询带 user_id             │
              │   ❌ 查询跨多个 user_id → 广播查询     │
              └───────────────────────────────────────┘
              ┌─ 事务边界一致? ───────────────────────┐
              │   ✅ 同一用户的数据在同一分片          │
              │   ❌ 同一订单的产品跨分片 → 分布式事务  │
              └───────────────────────────────────────┘
              ┌─ 避免热点? ──────────────────────────┐
              │   ✅ 散列分片 (hash)                   │
              │   ❌ 自增ID范围分片 → 最新分片压力大    │
              └───────────────────────────────────────┘
```

**分片算法对比**：

```sql
-- 1. HASH 取模 (最简单, 扩容麻烦)
shard_key = user_id % 4
-- 问题: 从 4 片扩到 8 片, 所有数据重新分配

-- 2. 一致性 HASH (推荐, 弹性扩容)
-- 虚拟节点分布在 Hash 环上, 扩容只影响相邻节点
-- 数据迁移量: 只迁移约 1/N 的数据

-- 3. 范围分片 (查询友好, 但可能热点)
-- orders_2025:  created_at 2025-01-01 ~ 2025-12-31
-- orders_2026Q1: created_at 2026-01-01 ~ 2026-03-31
-- 问题: 2026-03-31 当天 QPS 可能全部打到 orders_2026Q1

-- 4. 地理分片 (多机房部署)
-- 华北用户 → 北京机房, 华南用户 → 广州机房
```

### ShardingSphere-JDBC 实战配置

> ShardingSphere 是 Apache 顶级项目，支持 Java/.NET/Go/Python，JDBC 模式无需额外部署代理层。

```yaml
# application.yml (Spring Boot + ShardingSphere-JDBC)
spring:
  shardingsphere:
    datasource:
      names: ds0, ds1                     # 两个物理库
      ds0:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://192.168.1.10:3306/db_0
        username: root
        password: ${DB_PASSWORD}
      ds1:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://192.168.1.11:3306/db_1
        username: root
        password: ${DB_PASSWORD}

    rules:
      sharding:
        tables:
          t_order:
            actual-data-nodes: ds$->{0..1}.t_order_$->{0..3}
            # → ds0.t_order_0, ds0.t_order_1, ..., ds1.t_order_3 (8个实际表)

            database-strategy:            # 分库策略
              standard:
                sharding-column: user_id
                sharding-algorithm-name: db-inline
            table-strategy:               # 分表策略
              standard:
                sharding-column: order_id
                sharding-algorithm-name: tbl-inline

        sharding-algorithms:
          db-inline:
            type: INLINE
            props:
              algorithm-expression: ds$->{user_id % 2}
          tbl-inline:
            type: INLINE
            props:
              algorithm-expression: t_order_$->{order_id % 4}

    props:
      sql-show: true                     # 打印真实 SQL (调试用)
      sql-simple: false
```

**广播表（全局表）— 每个分片都有的小表**：

```yaml
# 字典表 (t_dict) 在每个数据源都有完整副本
rules:
  sharding:
    broadcast-tables:
      - t_dict
      - t_country
      - t_config
# JOIN 时无需跨库: SELECT o.*, d.name FROM t_order o JOIN t_dict d ON o.status = d.code
```

**绑定表 — 避免笛卡尔积**：

```yaml
# t_order 和 t_order_item 按相同的分片键分片, 且分片策略一致
rules:
  sharding:
    binding-tables:
      - t_order, t_order_item
```


### 读写分离下的数据一致性处理

> ⚠️ **核心矛盾**：主从复制有延迟（通常 < 1s），刚写入主库的数据可能还没同步到从库。

```sql
-- ❌ 问题场景: 写后立即读
-- 应用层代码:

-- 在应用层维护一个 ThreadLocal 标记:
-- if (刚刚执行了写操作):
--     读主库
-- else:

-- ✅ 方案2: 延迟阈值监控
```

### 主从复制原理

```
════════════════════════════════════════════════════════
          MySQL 异步复制流程 (经典主从)
════════════════════════════════════════════════════════

  ┌─────────┐                    ┌─────────┐
  │  Master │                    │  Slave  │
  └────┬────┘                    └────┬────┘
       │                              │
  ┌────▼─────────────────────┐   ┌────▼─────────────────────┐
  │ ① Binlog Dump Thread    │   │ ④ SQL Thread             │
  │    读取 binlog 发送给从库 │   │    执行 relay log 中的事件│
  └────┬─────────────────────┘   └────▲─────────────────────┘
```

```bash
# 恢复演练脚本 (MySQL + XtraBackup)

  --incremental-dir=$BACKUP_DIR/inc/20260811

cp -r $BACKUP_DIR/full/20260809/* $RESTORE_DIR/

systemctl start mysql

  && echo "✓ 恢复成功! 数据一致性校验通过" \
```

### 1. 什么是数据库三大范式？举例说明。

**第一范式 (1NF)**：列不可再分（原子性）。

```sql
-- ❌ 违反 1NF
CREATE TABLE students (id INT, phones VARCHAR(200));
INSERT INTO students VALUES (1, '13800138000,13900139000');
-- phones 列包含多个值!

-- ✅ 满足 1NF
CREATE TABLE student_phones (student_id INT, phone VARCHAR(20));
INSERT INTO student_phones VALUES (1, '13800138000'), (1, '13900139000');
```

**第二范式 (2NF)**：满足 1NF，且非主键列完全依赖于主键（消除部分依赖）。

```sql
-- ❌ 违反 2NF: (学号, 课程号) 联合主键, 但 "姓名" 只依赖于 "学号"
-- 成绩表: 学号(PK), 课程号(PK), 姓名, 课程名, 成绩
-- 姓名只依赖学号 → 部分依赖 → 拆表

-- ✅ 满足 2NF: 拆成学生表 + 课程表 + 成绩表
```

**第三范式 (3NF)**：满足 2NF，且非主键列不传递依赖于主键。

```sql
-- ❌ 违反 3NF: 学号 → 系编号 → 系主任
-- 学生表: 学号(PK), 系编号, 系主任
-- 系主任传递依赖于学号 → 拆表

-- ✅ 满足 3NF: 学生表(学号, 系编号) + 系表(系编号, 系主任)
```

> 🎯 **软考真题**：「关系模式 R(U,F) 属于第几范式」类题目每年必考。

### 2. B+Tree 索引为什么比 B-Tree 更适合数据库？

- **B+Tree 数据只存叶节点**：非叶节点只存 key，一个 16KB 页能存更多 key → 树的高度更低 → 磁盘 I/O 更少
- **叶节点双向链表**：支持高效范围查询（`BETWEEN`, `>`, `<`），B-Tree 需要中序遍历
- **查询稳定**：每次查询必须到叶节点，时间复杂度恒定

### 3. MySQL 中 `COUNT(*)` vs `COUNT(1)` vs `COUNT(column)` 的区别？

```sql
-- COUNT(*) = COUNT(1): 统计行数 (含 NULL 行), 性能相同 (MySQL 8.0+ 优化后)
-- COUNT(column): 统计该列非 NULL 的行数
-- COUNT(DISTINCT column): 统计该列去重非 NULL 的行数

-- 性能: COUNT(*) ≈ COUNT(1)  >  COUNT(id) >  COUNT(column)
-- MyISAM 的 COUNT(*) 最快 (表有行数缓存), InnoDB 需要扫描索引
```

### 4. MySQL 的 `VARCHAR` vs `CHAR` 如何选择？

| 类型 | 存储 | 适用场景 |
|------|------|----------|
| `CHAR(N)` | 定长, 尾部填空格 (最长255) | 固定长度: 手机号、身份证、MD5 |
| `VARCHAR(N)` | 变长, 1-2字节存长度 (最长65535) | 变长: 姓名、邮箱、地址 |

> ⚠️ `VARCHAR(255)` 不是万能选择——如果所有值都是固定长度（如 11 位手机号），CHAR(11) 效率更高。

### 5. 聚簇索引 vs 非聚簇索引的区别？

| 维度 | 聚簇索引 (Clustered) | 非聚簇索引 (Secondary) |
|------|---------------------|------------------------|
| 数据存储 | 叶节点 = 完整行数据 | 叶节点 = 索引列 + 主键值 |
| 数量限制 | 每表只能有 1 个 | 可以有多个 |
| 回表 | 不需要 | 需要 (除非覆盖索引) |
| 物理排序 | 按主键顺序 | 按索引列顺序 |

> MySQL InnoDB 的 PRIMARY KEY 就是聚簇索引。如果你没定义主键，InnoDB 会用第一个 UNIQUE 索引或自动生成 6 字节 ROWID。

### 6. 为什么建议用自增 ID 做 InnoDB 主键？

- **插入效率高**：新行总是追加到最后一页，不会引起页分裂
- **空间局部性好**：相邻主键的数据在同一页，范围查询 I/O 少
- **二级索引体积小**：二级索引的叶节点存的是主键值，自增 INT(4B) 比 UUID(36B) 小 9 倍

```sql
-- ❌ UUID 主键: 随机插入 → 频繁页分裂 → B+Tree 碎片化
-- ✅ 自增 ID: 顺序插入 → 追加写入 → B+Tree 紧凑
CREATE TABLE users (id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY, ...);
```

### 7. `EXISTS` vs `IN` 如何选择？

```sql
-- IN: 子查询结果集小 → 外层驱动
-- EXISTS: 外层结果集小 → 子查询驱动

-- IN 适用: 子查询结果集小
SELECT * FROM orders WHERE user_id IN (SELECT id FROM users WHERE status = 'vip');
-- 如果 vip 用户只有 100 个, IN 很快

-- EXISTS 适用: 外层结果集小
SELECT * FROM users WHERE EXISTS (
  SELECT 1 FROM orders WHERE user_id = users.id AND amount > 10000
);
-- 如果 users 只有 100 个, EXISTS 很快
```

> **生活类比**：IN 是"给你一个名单，去查这些人有没有购买记录"；EXISTS 是"挨个查每个人，看看他有没有大额购买"。

### 8. 为什么不建议用 `SELECT *`？

- 增加网络传输 (不需要的列也传了)
- 无法使用覆盖索引 (SELECT * 必须回表取全部列)
- 表结构变更 (加列) 可能影响结果集映射
- 无法判断哪些列真正被业务需要

### 9. MySQL 行级锁有哪几种？

```sql
-- 1. Record Lock (记录锁): 锁定单行索引记录
SELECT * FROM users WHERE id = 1 FOR UPDATE;  -- 锁 id=1 这一行

-- 2. Gap Lock (间隙锁): 锁定索引记录之间的间隙
SELECT * FROM users WHERE id BETWEEN 10 AND 20 FOR UPDATE;
-- 锁 (10, 20) 之间的间隙, 防止插入

-- 3. Next-Key Lock (临键锁): Record + Gap
-- 锁住当前记录 + 前面的间隙
-- InnoDB RR 级别默认使用, 防止幻读
```

### 12. Redis 缓存穿透、击穿、雪崩怎么解决？

| 问题 | 现象 | 解决方案 |
|------|------|----------|
| **缓存穿透** | 查不存在的数据，缓存和DB都没有 → 每次都打DB | 布隆过滤器 / 缓存空值 (短过期) |
| **缓存击穿** | 热点key过期瞬间，大量请求打DB | 互斥锁更新 / 永不过期 + 异步刷新 |
| **缓存雪崩** | 大量key同时过期，DB瞬间压力过大 | 过期时间加随机值 / 多级缓存 / 限流降级 |

### 19. 数据库索引为何用 B+Tree 而不用红黑树、AVL 树？

**核心原因：磁盘 I/O 模型不同。**

- 红黑树/AVL 树是**内存数据结构**，每个节点存一个值，树很高 → 磁盘 I/O 次数多
- B+Tree 是**磁盘数据结构**，每个节点是一个页 (16KB)，存几百个 key → 树高 3-4 层 → 3-4 次磁盘 I/O 即可定位数据
- 数据库数据量大，内存放不下，必须考虑磁盘访问模式

| **关系代数** | σ(选择), π(投影), ⋈(连接), ∪(并), −(差), ×(笛卡尔积) |

| **数据库完整性** | 实体完整性(主键非空唯一), 参照完整性(外键), 用户自定义完整性 |
| **封锁粒度** | 表级锁 < 页级锁 < 行级锁 (粒度越小并发越高) |
| **可串行化调度** | 多个事务并发执行的结果 = 某个串行执行的结果 |
| **两段锁协议(2PL)** | 扩展阶段(只加锁)+收缩阶段(只解锁) → 保证可串行化 |
| **数据库故障** | 事务故障(undo), 系统故障(redo), 介质故障(备份恢复) |
